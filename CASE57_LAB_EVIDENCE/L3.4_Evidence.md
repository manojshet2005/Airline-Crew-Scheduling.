### Reproducible, isolated procedure for later

Do not introduce a failing change on `feature/weekly-limit` or merge it. When an authenticated Jenkins instance is available:

1. Create a separate, unmerged lab branch from the verified feature head and add a focused test requiring `validate_duty(10, 40, 10)` to be accepted.
2. On only that branch, temporarily change the daily condition from `hours_today > 10` to `hours_today >= 10`. Keep the test asserting the inclusive boundary; run it locally once to verify it fails for the intended reason.
3. If the Jenkins job uses its inline Pipeline definition, temporarily set its explicit Checkout branch to the lab branch. Preserve authenticated checkout and CSRF; do not enable local checkout or weaken security. If branch publication is required for Jenkins SCM access, use a temporary, unmerged branch only with authorization; do not push the seeded defect to the feature branch.
4. Trigger a build through the authenticated Jenkins UI/API. Save the build URL, full console log and a genuine screenshot. Verify the Test stage fails and Package is skipped.
5. Restore the boundary predicate to `>`, rerun the same test, trigger a second Jenkins build, and save its successful console log/screenshot. Verify the Test and Package stages complete.
6. Restore the job's original branch configuration. Do not merge the experiment branch. Record exact build IDs and actual results; keep both logs.
